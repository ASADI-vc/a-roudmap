- **Original summary (own words):** The Twelve-Factor App is a concise methodology for building software-as-a-service applications, distilled from the authors' Heroku platform experience. It defines twelve practices — codebase, dependencies, config, backing services, build/release/run, stateless processes, port binding, concurrency, disposability, dev/prod parity, logs as event streams, and admin processes — each with its own page. The introduction frames the factors as enabling portability, cloud deployment, continuous deployment, and scaling, and states the methodology applies to apps in any language with any backing services.
- **Relevant content for curriculum:**
  - Introduction benefits as served: declarative setup automation; "clean contract with the underlying operating system, offering maximum portability"; suitability for "deployment on modern cloud platforms"; minimize divergence between dev and production "enabling continuous deployment"; scale up "without significant changes to tooling, architecture, or development practices". Scope line: "The twelve-factor methodology can be applied to apps written in any programming language, and which use any combination of backing services (database, queue, memory cache, etc)."
  - Background: Heroku-platform experience; format "inspired by Martin Fowler's books Patterns of Enterprise Application Architecture and Refactoring"; motivation to "raise awareness of some systemic problems", provide shared vocabulary, and offer conceptual solutions.
  - "Who should read this document?": "Any developer building applications which run as a service. Ops engineers who deploy or manage such applications."
  - The Twelve Factors, titles and one-line definitions exactly as served: I. Codebase — "One codebase tracked in revision control, many deploys"; II. Dependencies — "Explicitly declare and isolate dependencies"; III. Config — "Store config in the environment"; IV. Backing services — "Treat backing services as attached resources"; V. Build, release, run — "Strictly separate build and run stages"; VI. Processes — "Execute the app as one or more stateless processes"; VII. Port binding — "Export services via port binding"; VIII. Concurrency — "Scale out via the process model"; IX. Disposability — "Maximize robustness with fast startup and graceful shutdown"; X. Dev/prod parity — "Keep development, staging, and production as similar as possible"; XI. Logs — "Treat logs as event streams"; XII. Admin processes — "Run admin/management tasks as one-off processes".
